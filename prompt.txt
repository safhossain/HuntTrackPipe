I want to implement the new product by TypeSafe "Jev" as a complimentary pre-LLM filter + few other actions.
From what I know, Jev has 3 output types: noul, choice, and score. We will be using the first two.

What I plan to do is essentially provide the big blob of text from a job posting to Jev, it will act as a pre-LLM filter.
This is because Jev is not really a 'parser' in the sense of extracting specific information from a text. But it will
be useful to determine what at least *exists* or *classifying* some text. 

Jev will then return a NOUL question or choices for *LLM Output Schema Creation*.

Columns:AssociatedJevOutputType[noul question or choices]
Requisition_ID:NOUL[Does a Requisition ID exist in the text?]
Organization:NOUL[Can we determine the Organization from the text?]

Work_Mode:CHOICE[In-person, Hybrid, Remote, Travel, TBD, Unknown]

Applied_Date:N/A Not Sent To Jev or LLM. Will be manually added by user to HuntTrackPipe Engine and/or modified by user in Excel file.
Posting_URL:N/A Not Sent To Jev or LLM. Will be manually added by user to HuntTrackPipe Engine and/or modified by user in Excel file.
Application_Status:Not sent to Jev or LLM. Will be manually added by user to HuntTrackPipe Engine and/or modified by user in Excel file.
Recruiter_Name:NOUL[Can we determine the Recruiter Name from the text?]

So, the above items with NOUL or CHOICE will be sent to Jev for evaluation.

Then, we will dynamically + deterministically generate a output-schema (json structured output) for the 
remote LLM call to use. Of course, we will still need to send the original blob of text (job posting) to the LLM

The Engine, per session, should perform the following actions:
1. Do File System operations. This means creating subdirectories for each application.
- subdirs will live in \Applications
- subdirs will be named {Requisition_ID}_{Organization_Name}_{Position_Title}_{Applied_Date}
- Based on what is and what is NOT available from the job posting, the file name will replace it with "null" in
the position. spaces in between words will be replaced with hyphens.
Example (all 4 available):
1234567890_Google_Software-Engineer_2026-01-01
Example (no Requisition_ID):
null_Google_Software-Engineer_2026-01-01
example (no req id and org name):
null_null_Software-Engineer_2026-01-01

It is extremely unlikely that all four are not available. In the rare case where the first three are not available,
and only date applied is available, the subdir name will be null_null_null_{Date_Applied}_{timestamp}. Where timestamp
can simply be UNIX timestamp for uniqueness guarantee. But this does NOT mean {timestamp} will exist in all subdir names.
Only in the rare case where the first three are not available.

As for files within the subdirs:
If multi-file upload, keep all the individual files in the subdir aswell as the final combined file. The individual
files will be named as: {count (0, 1, 2, 3, ...)}_<file_name>.{file_extension}. 

Regardless if multi-file upload or not, the final combined file should be named as: 
{Candidate_Name}_{X}.{file_extension}, Where X is determined by the following priority:
    1. Requisition_ID
    2. Organization_Name+Position_Title
    3. Organization_Name
    4. Position_Title
    5. Applied_Date

2. Update the Excel file rows accordingly. Each session = 1 row = 1 application (I guess)
